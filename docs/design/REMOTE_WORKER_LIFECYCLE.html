三种用法生命周期 — 本地 / 远程沙箱 / 独立节点

一次任务从下发到结束，每一步"发生在哪、谁能碰到什么、恶意代码能做到哪一步"

① 三种用法怎么选

A 本地会话（默认）

ion "任务"
大脑Mac
手脚Mac
KeyMac
会话Mac
风险全部落在 Mac
日常可信工作：改自己的代码、查资料。已有两道 P0 防线（hooks 信任门 + 配置写保护）。

B 远程沙箱（客户端模式）

agent 调 spawn_worker(host="win38")
大脑win38（worker 整体搬家）
手脚win38
Key无（经 Mac 桥接）
会话Mac（实时回流）
风险困在 win38 沙箱里
不可信仓库分析、重编译、重活。打穿了也只是 win38。

C 独立节点（服务端模式）

ion38 "任务"（SSH 直达 win38）
大脑win38
手脚win38
Keywin38（你自己的代理 URL）
会话win38
风险独立核算，与 Mac 无关
无人值守定时任务、Mac 关机也要跑的活。WOL 唤醒 + 开机自愈。

② 生命周期 A：本地会话（日常默认）

全部发生在 Macion "帮我改这个 bug"
1
MacManager 在本机 spawn worker 进程会话文件落在 Mac ~/.ion/
2
Macagent 循环启动 → 用 Mac 的 key 直接调 LLMGLM 思考 → 返回工具调用计划
3
Mac工具执行：read / write / bash / grep 全部落在本机磁盘受保护路径检查（config.json 等写不进去 ✅）+ CommandGuard 拦高危命令
⚠
风险点（诚实声明）
① 恶意仓库的 build.rs 会在 Mac 上跑（LSP cargo check 触发）② bash 命令字符串可绕过检查 ③ hooks 已有信任门 ✅（项目级默认不加载）④ 配置写保护 ✅（[Protected] 拒绝）
结论：A 模式 = 全权限。可信工作用它没问题；不可信任务 → 用 B
4
Mac会话完整记录（含所有工具结果）→ 结束JSONL 只追加，可回放可审计

② 生命周期 B：远程沙箱（不可信任务 / 重活）

大脑和手脚整体搬到 win38，Mac 只出"门厅"agent 自主调 spawn_worker(host="win38", task="分析这个仓库")
1
MacManager 收到 spawn 请求 → refresh 自愈：经 22 管理通道拉起 WSL sshd + 刷新端口转发每次 spawn 前执行——VM 停机/IP 漂移自动修复（已实测两次重启零干预）
2
win38资产包下发：Mac 的 skills/agents 打包推送（便携性 lint 剔除含宿主路径的文件）；远端项目级 hooks.json 不加载（供应链免疫）声明式同步：远端 = 本次下发的精确镜像
3
win38SSH 拉起远端 worker（强制 fork 模式，独立会话文件）→ agent 循环在 win38 诞生Mac 上没有这个进程——它不存在于你的本机
4
win38零 key LLM 桥接：需要调 LLM 时发 llm_request → Mac 用真 key 代发 → 流式回传win38 的 key 可以是假的（实测摘除后照常出答案 "42"）——被打穿也偷不到钥匙
5
win38工具执行：read / bash / grep 全在 win38 磁盘；后台进程也是 win38 的子进程Mac 路径对它不存在——两个文件系统互不可见（这是隔离的根基，不是缺陷）
6
win38会话双写：远端照写本地副本 + 每条 entry 实时镜像回 Mac 落盘打穿/销毁/重装 win38 都不丢历史；UI 在 Mac 直读 ✅
7
Mac想读 Mac 文件 / 经 Mac 出网？→ 封闭动词表：fs.read / fs.write / http.fetchgrants 默认全拒 → ask_on_deny 转人工审批（RPC verb_review 放行）→ 每次调用审计留痕；永远没有 host.bash 动词
8
win38任务完成 / SSH 断线 = worker 死亡 → 远端临时目录清理Mac 侧只剩会话历史；kill / 断线都不影响 Mac 任何东西

② 生命周期 C：独立节点（无人值守）

win38 是一台自治机器，Mac 关机它照跑win38-on → ion38 "定时检查 xx 并汇报"
1
win38机器关着？→ win38-on 发 WOL 魔术包唤醒（实测 23 秒）→ SSH/服务自动就绪（约 2 分钟）开机计划任务自动拉起 ion serve + WSL 网关，零人工干预（实测两轮重启）
2
win38win38 自己的 ion serve 接单：agent / 工具 / 会话 / 定时任务 全部自治用它自己的 config + 你自己的代理 URL 调 LLM（Mac 不参与）
3
win38用完：win38-off 远程关机省电；下次要再唤醒即可
⚠
风险点
它持有你代理的 URL（可烧你代理的底层额度——但 URL 管理权在你手里，随时可在代理侧封禁）。已被 SSH 密码登录已关闭 ✅，只认 Mac 公钥。

③ "有没有这种可能"——恶意代码能做到哪一步

前提：你让 agent 分析一个恶意仓库，它执行了里面的恶意代码。逐个回答"会不会影响到……"。

B 模式下，它能删除我 Mac 上的文件吗？
不能。两个文件系统互不可见：win38 上不存在 /Users/ 路径，Mac 上不存在它的沙箱路径。唯一跨机通道是封闭动词表（fs.read/fs.write 默认全拒 + 审批），且没有 "在 Mac 执行命令" 这个动词。
例外：你主动授权 fs.write 某个 Mac 路径 + 审批放行——那是你点头的，且每次留审计。
B 模式下，它能偷走我的 LLM key 吗？
不能。桥接模式下 worker 的 config 里没有 key（实测摘成假值照常工作）。它调 LLM 的唯一方式是请求 Mac 代发。真 key 从未离开 Mac。
C 模式（ion38）下 win38 持有你代理的 URL——但那是你自己的代理，随时可在代理侧封禁/限流。
B 模式下，它能反过来攻击我的 Mac 吗？
没有现成通道。不能 SSH 回 Mac（没有你的钥匙）、不能写 Mac 文件（无动词）、出网只能走白名单域名。它能"看见"的只有：任务给它的数据 + 白名单内的网络。
残余面：烧 token（有预算封顶）；同网段扫描 NAS（内网设备照常设防即可）。
A 模式（本地）下呢？
能——这就是 A 模式的本质。本地 = agent 有 Mac 全权限。已堵：hooks 供应链（信任门）✅、配置改写（写保护）✅。仍可绕：bash 字符串（echo x > 文件）。
结论：不可信的东西，别用 A 模式跑——用 B。这正是 B 存在的意义。
LLM 提供商（zai）能看到我的数据吗？
会话内容都会发给它——这是任何 AI 工具的固有属性，三种模式相同（B 模式经 Mac 桥接发出，路径多一跳但终点相同）。
所以秘密本身别放进会话；工具读到的敏感文件内容也会进上下文——verb 审批就是最后一道闸。
它能让我的 Mac 服务挂掉吗（比如杀 ion serve）？
不能。B 模式的 worker 是 win38 里的进程，够不着 Mac 的进程表。反向才需要警惕：你 Mac 上杀远端 worker 随便杀，不影响本机。
最坏情况：烧 token + 消耗 win38 资源 → kill worker / win38-off 随时止损。

④ 实操命令卡

# ── A 本地（日常）──
ion "帮我改这个 bug"

# ── B 远程沙箱（不可信 / 重活）──
# 让 agent 自己派（推荐——它会按需给 win38 分配子任务）：
ion "在远程沙箱里分析 /tmp/这个仓库 有没有安全问题，spawn_worker 时用 host=win38"
# 或手动指定：
ion rpc --method create_worker --params '{"host":"win38","agent":"build","initial_prompt":"..."}'

# ── C 独立节点 ──
win38-on                      # 唤醒（关机状态时，约 2 分钟自动就绪）
ion38 "检查 xx 服务状态"      # 直接指挥 win38 上的 ion
win38-off                     # 用完关机
实测锚点：零 key 桥接（win38 key 摘除后答出 "42"）· 会话回流 UI 直读 · 越权 verb_denied + 审计 · 重启零干预恢复 ×2 · WOL 23s 唤醒 · 源码：worker_registry.rs（spawn）· provider_bridge.rs（桥接）· host_tools.rs（动词）· hooks/mod.rs（信任门）· protected_paths.rs（写保护）
