# AUTO-RECOVERY 可靠性分析

## ✅ 已验证覆盖的场景

| 场景 | 可靠性 | 验证方式 |
|------|--------|---------|
| 远程 worker 被杀（pkill/SIGTERM） | ✅ 高 | 真机验证：杀→2s 检测→2s 重派→断点续作 |
| SSH 连接断开（网络瞬断 >5min） | ✅ 高 | 同上（worker 是 ssh 子进程，断=死） |
| Worker 崩溃（panic/OOM） | ✅ 高 | 同上（stdout EOF + exit_code ≠ 0） |
| 正常完成不误触发 | ✅ 高 | 第二轮验证确认（agent_end 后不重派） |
| 本地 worker 不触发 | ✅ 高 | 单测验证 |
| 防死循环（3 次上限） | ✅ 高 | 代码逻辑保证 |

## ⚠️ 部分覆盖 / 有条件的场景

| 场景 | 问题 | 影响 |
|------|------|------|
| 会话镜像滞后 | M3 回流是近实时但非事务性的——worker 刚写完条目就死，最后 1-2 条可能没到 Mac | resume prompt 缺最后一步的上下文 |
| 复杂任务断点续作 | resume prompt 只含原始任务 + 最后一条文本/工具调用（截断 300/400 字），不含完整对话历史 | 替补 LLM 可能做出与原 worker 不同的决策 |
| LLM 不听指令 | 替补收到"不要重头开始"但 LLM 可能忽略 | 重复已完成的步骤（浪费但不致命） |
| 网络恢复延迟 | 替补 spawn 需要 SSH 到 win38——如果 WSL/portproxy 还没恢复，spawn 失败 | refresh 机制会尝试修复，但如果 win38 本身宕机则无法恢复 |

## 🔧 加固后的状态（2026-09-12 更新，commit 980b422）

三大加固已落地并真机验证：

| 原漏洞 | 修法 | 验证 |
|--------|------|------|
| SSH 僵尸（🔴） | 心跳超时 Busy>10min → auto-recovery（bin/ion.rs 心跳循环内收集+循环外处理） | 编译+单测（真机需等 10min 自然超时） |
| resume prompt 摘要（🟡） | 传最近 6 条完整对话（约 3 轮），含 [用户]/[AI]/[调用了工具] 标记 | 真机：替补收到完整上下文续作 |
| 恢复通知（🟢） | auto_recovered UI 事件广播（stdout_eof + heartbeat_timeout 两个触发源） | 真机：ion subscribe 实测收到 ✅ |

## ❌ 未覆盖 / 已知漏洞（加固后剩余）

| 场景 | 为什么不覆盖 | 严重度 |
|------|-------------|--------|
| SSH 僵尸（连接挂着但没数据） | stdout 没有 EOF，Manager 不知道 worker 死了 | 🔴 高——需要心跳超时检测 |
| exit_code = 0 但任务没完成 | agent 循环正常退出但实际失败了——auto-recovery 不触发 | 🟡 中——需要任务级完成度检查 |
| 本地 worker 崩溃 | 只覆盖远程 worker | 🟡 中——本地有 file-snapshot 回滚 |
| 替补也死了（根因未修） | 3 次重试后放弃 | 🟡 中——如果 win38 资源耗尽，3 次都不够 |
| 用户不知道发生了恢复 | 没有通知/事件广播 | 🟢 低——日志有记录但没有 UI 提示 |
| 多 worker 同时死 | 每个都独立重派——5 个 worker 同时死会同时 spawn 5 个替补 | 🟢 低——可能压垮远端 |
| resume prompt 是摘要不是完整上下文 | 替补 worker 的 LLM 只看到摘要，没有完整对话历史 | 🟡 中——复杂任务可能续作质量下降 |

## 总体可靠性估计

| 任务类型 | 估计可靠性 | 原因 |
|---------|-----------|------|
| 简单任务（文件操作/命令执行） | ~95% | 断点容易识别，恢复后能精确继续 |
| 中等任务（代码修改/测试修复） | ~80% | resume prompt 是摘要，可能缺关键上下文 |
| 复杂任务（多文件架构级开发） | ~70% | 摘要丢失太多决策链，替补可能走不同路线 |
| 级联故障（win38 本身宕机） | ~0% | SSH 不可达，无法 spawn 替补（需 WOL + refresh） |

## 最薄弱的三个环节（如果要继续加固）

1. **SSH 僵尸检测**——worker 死了但 ssh 连接挂着 → 需要心跳/超时机制
2. **完整上下文传递**——resume prompt 是摘要 → 可以把完整会话文件传给替补
3. **恢复通知**——用户不知道发生了恢复 → 加一个 UI 事件（auto_recovered）
